## Method

- Each run is `df.write.format("noop").mode("overwrite").save()`: every row is computed and nothing is written. Wall time is measured around that call. Inputs are read from Parquet in every run; nothing is cached.
- The median of the runs is reported, with the fastest and slowest. A difference smaller than the larger spread of the two variants is reported as within noise.
- Shuffle bytes, shuffle records and task counts are summed over the run's completed stages (`GET /api/v1/applications/{app}/stages/{stage}`: `shuffleReadBytes`, `shuffleWriteBytes`, `shuffleWriteRecords`, `numTasks`), from the median run. Peak task execution memory is the largest `peakExecutionMemory` of any task of any stage of any run (`GET .../stages/{stage}/{attempt}/taskSummary?quantiles=0.5,1.0`). The longest task is the largest `executorRunTime` of the median run, shown with the median task of the same stage, which says how uneven that stage was. The skew findings name the most uneven stage: the largest ratio of longest to median task among stages of two or more tasks whose longest task took at least 100 ms. Peak memory is Spark's execution memory (aggregation hash maps, sort buffers), not the JVM heap.
- After every run: a JVM garbage collection and a 5 s pause (not timed), so Spark's deletion of that run's shuffle files does not overlap the next run. One untimed warm-up round runs first, so code generation and the page cache are warm.
- The plan is the executed plan of the median run, the adaptive final plan (`GET .../sql/{execution}?planDescription=true`).
- Before timing, the variants of each group were run on a sample (every 20th book, including one book of the oversized desk) and their rows compared: the same keys, vectors equal to 1e-06 relative to their size. `vector_sum` 822 rows, `rollup` 45 rows, `skew_aggregate` 20 rows, `skew_join` 20 rows, `join` 822 rows, `shuffle_partitions` 822 rows.
- Salted variants use 16 salt values. The AQE skew variants set `spark.sql.adaptive.skewJoin.enabled=true`, `spark.sql.adaptive.forceOptimizeSkewedJoin=true`, `spark.sql.adaptive.skewJoin.skewedPartitionFactor=2`, `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes=64MB`.

Columns: median and min-max wall time in seconds; shuffle read and write in MiB; peak task execution memory in MiB; longest task (and its stage's median task) in seconds; tasks; key operators of the executed plan (bookkeeping nodes such as `Project` and query stages left out).
